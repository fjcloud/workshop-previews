Lab 3.1 — Usage, Performance and Cost

Review preview — PR 32, not the published workshop. This page comes from commit 1e0013a7541bd0e383bc58b6a9cd248a27df5f52 on branch docs/aro-guided-workshop-pr-preview. Read the changes and leave feedback in the pull request. The production workshop on main is unchanged. The clone command in Act 0 uses this review branch so its proposed manifests can be reviewed together.

Goal

Explore the installed dashboard to compare coding tokens, runtime-agent tokens and local GPU activity. Connect one app action to its usage graphs.

Persona: Developer + Platform Engineer
Time: 10 minutes
Outcome: Identify coding versus runtime token usage and relate app activity to requests, latency and GPU utilization.

Recover the console URL and choose the right account

Return to the cluster terminal, still signed in as workshop-admin:

Terminal: cluster — the shell beside this guide.

 
# Print the OpenShift console URL for this exact cluster.
oc whoami --show-console

Open that URL in the administrator browser profile, or sign out of the developer session first. Select identity provider workshop, username workshop-admin, and the administrator password you chose in Act 0.

Open the dashboard

  1. Open the OpenShift console using your environment’s access details and sign in as workshop-admin.

  2. Dismiss the welcome tour if shown. Go to Observe → Dashboards and select Workshop AI — ARO.

  3. Set the time range to Last 1 hour and the refresh interval to 30 seconds. Extend the range if you completed the earlier labs more than an hour ago.

The application generation, batch analysis and price checks from Act 2 have already produced activity.

Allow 2–3 minutes for a new action to appear in the dashboard. Refreshing the page immediately does not accelerate the monitoring scrapes. Keep the time range wide enough to include the action; cached analysis/research does not produce a new model call. A quiet graph is not by itself a monitoring failure.

Explore the existing activity

Look at What to identify

Model tokens by subscription

Compare deepseekv4pro-workshop (OpenCode/coding) with deepseekv4pro-card-scout (app/Playground research). These are cumulative totals combining input and output tokens.

Model requests accepted by quota checks

Find the activity around generation and price checks.

Quota rejections (HTTP 429)

Check whether MaaS rejected requests. Zero rejections is normal; no quota test is required. Foundry has a separate tokens-per-minute limit.

D3 completed scoring requests / request latency p95 / queued requests

Find the batch-analysis activity. D3 scores images rather than generating text tokens; latency can be empty when no requests completed in the recent window.

T4 utilization / memory

Compare the batch activity with quieter periods. Model memory remains allocated while idle. DeepSeek runs on Foundry, so a coding request does not use this T4.

Connect an app action to the graphs

  1. Keep the dashboard open in one tab and Card Scout in another.

  2. Choose an analyzed Pokémon card whose price you have not checked yet and click Check price. Note the time.

  3. After the next scrapes, find the increase for deepseekv4pro-card-scout in the token and request panels. The coding subscription should not increase because of this action.

  4. Compare with the T4 panels: price research uses DeepSeek and the MCP tool, while D3 was used earlier for image classification.

Completed analysis and successful price research are cached. Reopening saved results does not generate another inference request. A short request may also fall between GPU samples; low utilization alone does not mean it never ran.

Understand the limits and cost

In OpenShift AI → Settings → MaaS governance → Subscriptions, find the coding and runtime subscriptions. Click the count in each row’s Models column to see its token limit and time window. These are administrator views; use the workshop-admin session. Their allowances are ten million and one million tokens per 24 hours respectively. They govern consumption, not spending caps; the shared coding key reports workshop-level usage rather than individual participants.

The dashboard is not an Azure invoice. Its token total does not separate input, cached input and output rates. Foundry token pricing comes from your Azure agreement; the T4 VM, CPU workers and disks remain provisioned while idle.

Checkpoint

Explain which subscription powers OpenCode, which powers app research, and why price checks can consume tokens without increasing T4 activity. You explored the existing dashboard without querying Prometheus or running validation scripts.
